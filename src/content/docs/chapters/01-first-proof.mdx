## 本章目標

讀完本章，你應該能夠：

1. 在 VS Code 中打開課程專案，看到 Lean 的 **Infoview** 面板。
2. 讀懂一個 **proof state**：哪些是已知假設、哪一行是待證目標。
3. 逐行執行一個短證明，看著目標被「消掉」。
4. 知道 `sorry` 是什麼，以及為什麼「沒有錯誤訊息」不等於「證明完成」。
5. 第一次請 AI 解釋 Lean 的狀態，同時清楚哪些判斷仍然是你的責任。

如果你還沒有安裝環境，請先完成 [環境設定](../../guides/setup/)，再回到這裡。

## 為什麼要讓電腦檢查證明？

在數學課上，一個證明是否正確，通常由讀者（老師、審稿人、同學）判斷。讀者會跳過自己認為「顯然」的步驟，也可能漏看一個少寫的條件。證明輔助系統（proof assistant）換了一種做法：我們把定理與證明寫成一種精確的形式語言，再交給一個小而嚴格的程式去檢查每一步是否真的由規則推得。

Lean 就是這樣的系統。它同時是一個程式語言與一個證明檢查器。你寫下的每一個定理，都會被 Lean 讀成一個精確的陳述；你寫下的每一個證明，都會被逐步檢查。只要有一步說不通，Lean 就會在那一行標出紅色波浪線。

這帶來兩個直接後果：

- **好處**：被 Lean 接受的證明，不會因為「看漏了一個 case」而出錯。
- **代價**：Lean 只檢查「你寫下的陳述」是否被證明，**不會**替你檢查這個陳述是不是你心中想的那個數學命題。把數學翻譯成 Lean 的那一步，責任在人。

這個代價會貫穿整門課。當我們之後請 AI 協助時，它尤其重要：AI 可能為了讓 Lean 不再報錯，而悄悄把題目改成另一個更容易的題目。

## 讀懂 proof state

先看一個最小的例子（這是說明用的片段）：

```lean
example (p q : Prop) (hp : p) (hq : q) : p ∧ q := by
  constructor
```

把游標放在 `by` 之後、`constructor` 之前，Infoview 會顯示類似：

```text
p q : Prop
hp : p
hq : q
⊢ p ∧ q
```

讀法如下：

- `⊢` **上方**是「目前手上有的東西」：`p` 與 `q` 是兩個命題，`hp` 是 `p` 成立的證據，`hq` 是 `q` 成立的證據。
- `⊢` **下方**是「還要證明的目標」：`p ∧ q`。

`constructor` 的意思是：「要證明一個『且』，就分別證明兩邊。」執行後，目標會分成兩個：

```text
case left
⊢ p
case right
⊢ q
```

（實際顯示時每個目標上方都會重複列出假設，這裡省略。）接著用 `exact hp` 交出第一個目標的證據、`exact hq` 交出第二個，Infoview 最後會顯示 **No goals**。這就是一個完整證明的節奏：**讀目標 → 選一個動作 → 再讀新的目標**。

### `sorry`：暫時跳過，但不是完成

試著把某個證明的內容整個換成 `sorry`。你會發現 Lean **沒有**紅色錯誤，只在定理名稱下出現黃色警告，訊息大意是 declaration uses `sorry`。如果你在專案根目錄用終端機檢查這個檔案（例如 `lake env lean Course/First.lean`），它通常也會成功結束（exit code 0），只多印一行警告。

這是故意的設計：`sorry` 讓你先寫好整體結構，晚點再補細節。但這也代表：

> **編譯成功、沒有紅線、exit code 0，都不代表證明完成。**

可靠的檢查方法是對你的定理執行 `#print axioms`。如果輸出中出現 `sorryAx`，就表示某處（可能在你引用的另一個定理裡）仍然有 `sorry`。

另一方面，你也常會看到 `propext`、`Classical.choice`、`Quot.sound` 這三個名字。它們是 Lean 與 mathlib 普遍使用的標準公理，出現它們**不是**作弊。真正要警覺的是 `sorryAx`，以及任何你或 AI 自己用 `axiom` 宣告的新公理。

## AI 初體驗：請它解釋，而不是請它代勞

本課程的主線是「和 AI 一起把數學形式化」。從第一章就開始，但第一次的任務刻意很小：**請 AI 解釋，而不是請 AI 寫證明。**

找一個 proof state，例如上面 `constructor` 之後的狀態，把 Infoview 的文字整段複製給你使用的 AI 助理，並這樣問：

```text
以下是 Lean 4 的 proof state。請用中文逐行解釋：
1. ⊢ 上方每一行代表什麼；
2. 目前的目標是什麼；
3. 有哪一兩個 tactic 可能推進這個目標，以及為什麼。
請不要直接給我完整證明。

（貼上 Infoview 內容）
```

讀它的回答時，請自己確認三件事：

- 它對**量詞**與**假設**的描述，是否和 Infoview 中實際的文字一致？
- 它提到的 tactic，你能否在 Lean 裡實際試出來，而且結果和它描述的相同？
- 如果它說錯了，你能指出是哪一句嗎？

AI 的解釋可能流暢但不正確。Lean 會檢查證明，但**沒有東西會檢查 AI 的解釋**，除了你。在 [第 6 章](../06-agent-collaboration/) 之前，我們都只讓 AI 扮演「會說話的參考書」。

如果你沒有可用的 AI 帳號，也完全沒問題：本課程每一個 AI 步驟都可以改成「自己讀 Infoview、自己寫下解釋」，學到的東西是一樣的。

## 練習

### 練習 1.1　讀陳述

不看證明，只讀 `first-proof` 區段的陳述行，用一句完整的中文寫出它在說什麼，包括每個變數的型別。

<details>
<summary>提示</summary>

冒號 `:` 左邊括號裡的是「參數」：名字與它的型別。冒號右邊、`:=` 之前的是結論。像 `(n : ℕ)` 表示「對任意自然數 n」。

</details>

<details>
<summary>解答方向</summary>

一個好的翻譯會同時寫出：(1) 對哪些物件成立（「對所有自然數 n」之類）；(2) 有沒有前提；(3) 結論是什麼。如果你的句子沒提到型別，請補上：在 Lean 中，「對所有自然數」與「對所有實數」是不同的陳述。

</details>

### 練習 1.2　看見 `sorry`

在專案根目錄新增一個你自己的練習檔，例如 `Scratch.lean`（不要改 `Course/` 中的課程檔案），寫入下面的 `example`，用 `sorry` 當證明，然後觀察 Infoview 與編輯器中的訊息。也可以在終端機執行 `lake env lean Scratch.lean`，確認它雖然印出警告，仍然成功結束。接著把 `sorry` 換成正確的證明。

```lean
example (p : Prop) (hp : p) : p := by
  sorry
```

<details>
<summary>提示</summary>

目標是 `p`，而假設中剛好有一個 `hp : p`。要「交出」一個剛好符合目標的證據，用哪個 tactic？

</details>

<details>
<summary>解答</summary>

把 `sorry` 換成 `exact hp`。改好之後黃色警告應該消失。再執行一次 `lake env lean Scratch.lean`，輸出中應該不再有 sorry 警告。

</details>

### 練習 1.3　檢查 AI 的解釋

用上面的 Prompt 請 AI 解釋 `first-proof` 中任一行之後的 proof state。找出它的回答中**至少一處**你需要回到 Lean 實際驗證的說法，並驗證它。

<details>
<summary>提示</summary>

最容易驗證的說法是「執行某某 tactic 之後，目標會變成……」。把游標移到那一行之後，直接比對。

</details>

<details>
<summary>參考做法</summary>

把 AI 的說法與 Infoview 實際內容並排寫下，標記「一致」或「不一致」。若不一致，以 Lean 為準，並寫一句話說明 AI 錯在哪裡。這份紀錄的習慣，會在之後的實戰中變成正式的修復紀錄。

</details>

## 本章小結

- proof state 中，`⊢` 上方是假設，下方是目標。
- 證明的節奏是：讀目標、做一步、再讀目標，直到 No goals。
- `sorry` 讓檔案能編譯，但不代表完成；用 `#print axioms` 檢查有沒有 `sorryAx`。
- AI 從第一章就能幫你**解釋**，但陳述的意義、量詞與假設，必須由你確認。
