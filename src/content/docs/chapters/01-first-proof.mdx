## 本章目標

1. 在 VS Code 中打開課程專案，讀懂 Infoview 上的「已知」與「目標」。
2. 把一個課本上的短證明，一行一行對到 Lean，看著目標被消掉。
3. 知道「沒有紅線」不等於「證明完成」，會用 `#print axioms` 檢查。

如果你還沒有安裝環境，請先完成 [環境設定](../../guides/setup/)，再回到這裡。

## 為什麼要讓電腦檢查證明？

在數學課上，證明對不對，通常由讀者（老師、助教、審稿人）判斷。讀者會跳過自己覺得「顯然」的步驟，也可能漏看一個少寫的條件。

Lean 換了一種做法：我們把定理與證明寫成精確的形式語言，再交給一個小而嚴格的程式檢查每一步。只要有一步說不通，Lean 就在那一行標出紅色波浪線。

這帶來兩個直接後果：

- **好處**：被 Lean 接受的證明，不會因為「看漏了一個 case」而出錯。
- **代價**：Lean 只檢查「你寫下的陳述」有沒有被證明，**不會**替你檢查這個陳述是不是你心中的那個數學命題。把數學翻成 Lean 的那一步，責任在人。

這個代價會貫穿整門課。之後請 AI 幫忙時尤其要記得：AI 可能為了讓 Lean 不再報錯，悄悄把題目改成另一個比較容易的題目。

## 先在紙上，再到 Lean

先看一個離散數學第一週就會遇到的證明：「若 $P$ 成立且 $Q$ 成立，則 $P \land Q$ 成立」。左欄是作業上的寫法，右欄是對應的 Lean。

<PaperVsLean file="Course/University.lean" region="uni-and-intro" rows={["2", "3", "4", "5"]}>
  <Fragment slot="p1">**定理**：設 $P, Q$ 是命題。已知 $P$ 成立、$Q$ 成立，則 $P \land Q$ 成立。</Fragment>
  <Fragment slot="p2">要證明「且」，分成兩件事：證 $P$，再證 $Q$。</Fragment>
  <Fragment slot="p3">第一件：$P$ 就是已知條件。</Fragment>
  <Fragment slot="p4">第二件：$Q$ 也是已知條件。證畢。</Fragment>
</PaperVsLean>

先讀第一行。`theorem` 後面是定理名稱；冒號前的括號是參數與已知條件，`(P Q : Prop)` 是「P、Q 是命題」，`(hp : P)` 是「P 成立，證據叫 hp」；冒號後、`:=` 前的 `P ∧ Q` 是結論。`by` 之後就是證明。

<Term term="tactic" short="證明中的一個動作，例如「分成兩個子目標」或「交出現成的證據」。">

`by` 後面一行一行寫的指令就是 tactic。上面的 `constructor` 與 `exact` 都是。每執行一個 tactic，Infoview 就會顯示新的「已知」與「目標」。tactic 不是魔法，它只是把課本上「我們接下來證明……」這類句子，變成電腦能檢查的步驟。

</Term>

## 讀懂 Infoview

把游標放在 `constructor` 那一行之前，Infoview 顯示的東西叫做這個位置的**證明狀態**：

<Term term="proof state（證明狀態）" short="證明寫到某一行時，「手上有什麼」與「還要證什麼」的清單。">

Infoview 中以 `⊢` 為分界：上方每一行是一個已知的東西（變數或假設），格式是「名字 : 型別」；下方是目前的目標。目標可能不只一個，這時每個目標會各自列出它能用的已知，並以 `case 名稱` 標示。

</Term>

接下來每寫一行，目標就變一次。下面列出 `uni_and_intro` 每一步之後 Infoview 的內容，你可以在 VS Code 中逐行移動游標對照：

<GoalSteps
  title="uni_and_intro 的目標如何一步步變化"
  start={"P Q : Prop\nhp : P\nhq : Q\n⊢ P ∧ Q"}
  steps={[
    { tactic: 'constructor', note: '「要證且，就分別證明兩邊」。一個目標變成兩個。', goal: 'case left\n⊢ P\n\ncase right\n⊢ Q' },
    { tactic: '· exact hp', note: '處理第一個目標：hp 剛好是 P 的證據，直接交出。', goal: 'case right\n⊢ Q' },
    { tactic: '· exact hq', note: '處理剩下的目標：交出 Q 的證據。', goal: 'No goals' },
  ]}
/>

（為了版面，這裡省略了每個目標上方重複列出的 `P Q : Prop`、`hp : P`、`hq : Q`。）

行首的 `·` 表示「現在專心處理其中一個目標」，讓 Lean 的結構和紙上的「第一件、第二件」一樣清楚。整個證明的節奏就是：**讀目標 → 選一個動作 → 再讀新的目標**，直到 No goals。

## 課程檔案的第一個證明

`Course/First.lean` 的 `first-proof` 區段更短：

<LeanCode file="Course/First.lean" region="first-proof" />

**先讀陳述，再看證明。** 只讀 `theorem` 那一行，用一句完整的中文說出它在主張什麼：「對任意命題 $P$，若 $P$ 成立（證據叫 `h`），則 $P$ 成立。」一句好的翻譯要同時說出三件事：

1. 對哪些物件成立：這裡是「任意命題 P」。以後遇到 `(n : ℕ)` 就是「任意自然數 n」，而「對所有自然數」和「對所有實數」是不同的陳述。
2. 有哪些前提：這裡是 `h : P`。
3. 結論是什麼：這裡是 `P`。

再把游標放到 `exact h` 前後：之前目標是 `⊢ P`，`h : P` 就在上方；之後變成 No goals。

## `sorry` 與 `#print axioms`：檢查有沒有偷懶

寫證明時，可以先用 `sorry` 暫時代替還沒寫完的部分。Lean 遇到 `sorry` **不會**標紅線，只在定理名稱下出現黃色警告，大意是 declaration uses `sorry`；在終端機執行 `lake env lean 檔名` 也通常會成功結束（exit code 0）。

這是故意的設計：`sorry` 讓你先搭好整體結構，晚點再補細節。但也因此：

> **查核提示**：沒有紅線、編譯成功、exit code 0，都不代表證明完成。對你的定理執行 `#print axioms 定理名稱`，輸出中**沒有 `sorryAx`**，才代表沒有偷懶。

`first-check` 區段示範了兩個會一直用到的指令：

<LeanCode file="Course/First.lean" region="first-check" />

- `#check 名稱`：顯示這個名字的型別。對定理而言就是它的陳述。不確定一條引理在說什麼時，先 `#check`。
- `#print axioms 名稱`：列出這個定理最後依賴了什麼。`first_proof` 的輸出是 `'Course.first_proof' does not depend on any axioms`。如果某處（包括它引用的別的定理）還有 `sorry`，這裡就會出現 `sorryAx`。

<details>
<summary>補充：輸出裡出現其他名字怎麼辦？（標準公理）</summary>

用到 mathlib 的定理，`#print axioms` 常會列出 `propext`、`Classical.choice`、`Quot.sound` 這三個名字。它們是 Lean 與 mathlib 普遍使用的標準公理（命題外延性、選擇公理、商型別的公理），出現它們**不是**作弊。

真正要警覺的只有兩種：`sorryAx`，以及任何你或 AI 自己用 `axiom` 宣告的新公理。後者等於「直接宣布某件事成立」，Lean 會接受，但它沒有被證明。[第 8 章](../08-project-audit/) 的查核流程會把這件事做成固定步驟。

</details>

## 和 AI 一起學

本課程的主線是「和 AI 一起把數學形式化」。第一次的任務刻意很小：**請 AI 解釋，而不是請 AI 寫證明。** 把上面 `constructor` 之後的 Infoview 內容整段複製給 AI，請它逐行說明。

<AskAI
  task="把一個 proof state 交給 AI，請它解釋每一行，再由你回到 Lean 逐句核對。"
  prompt={"我在學 Lean 4，以下是 Infoview 顯示的 proof state。請用中文逐行解釋：\n1. ⊢ 上方每一行代表什麼；\n2. 目前有幾個目標，各是什麼；\n3. 有哪一兩個 tactic 可能推進目前的目標，執行後目標會變成什麼。\n請不要直接給我完整證明。\n\n（在這裡貼上 Infoview 內容）"}
>

- AI 對**已知**與**目標**的描述，和 Infoview 的實際文字一致嗎？目標的個數有沒有算對？
- 找出它說「執行某個 tactic 之後，目標會變成……」的句子，把那個 tactic 實際寫進 Lean，比對 Infoview。
- 把 AI 的說法和 Infoview 並排寫下，標記「一致」或「不一致」；不一致時以 Lean 為準，並寫一句話說明 AI 錯在哪裡。這個紀錄習慣，之後會變成實戰中的修復紀錄。

</AskAI>

AI 的解釋可能很流暢但不正確。Lean 會檢查證明，但**沒有東西會檢查 AI 的解釋**，除了你。在 [第 6 章](../06-agent-collaboration/) 之前，我們都只讓 AI 扮演「會說話的參考書」。

如果你沒有可用的 AI 帳號也沒關係：每一個 AI 步驟都可以改成「自己讀 Infoview、自己寫下解釋」，學到的東西是一樣的。

## 練習

### 練習 1.1　翻譯並證明

把「設 $P, Q$ 是命題。若 $P$ 成立且 $Q$ 成立，則 $Q \land P$ 成立」翻成 Lean 並證明。請在專案根目錄新增自己的練習檔（例如 `Scratch.lean`），不要改 `Course/` 中的課程檔案。

1. 先只寫陳述，證明用 `sorry`，觀察黃色警告；再加一行 `#print axioms my_and_swap`，看看輸出中的 `sorryAx`。
2. 對照本章的 `uni_and_intro`，檢查參數、假設與結論的**順序**是否和原句一致。
3. 把 `sorry` 換成真正的證明，再看一次 `#print axioms`。

```lean
theorem my_and_swap : sorry := by
  sorry

#print axioms my_and_swap
```

<details>
<summary>提示</summary>

陳述的形狀和 `uni_and_intro` 幾乎一樣：`(P Q : Prop) (hp : P) (hq : Q) : 結論`。注意結論是 `Q ∧ P`，不是 `P ∧ Q`，所以 `constructor` 之後第一個目標是 `Q`。

</details>

<details>
<summary>解答</summary>

```lean
theorem my_and_swap (P Q : Prop) (hp : P) (hq : Q) : Q ∧ P := by
  constructor
  · exact hq
  · exact hp

#print axioms my_and_swap
```

改好之後黃色警告消失，`#print axioms` 的輸出變成 `'my_and_swap' does not depend on any axioms`。如果你把結論寫成 `P ∧ Q`，Lean 一樣會接受，但那是另一個陳述；這正是「Lean 只檢查你寫下的陳述」的第一個例子。

</details>

## 本章小結

- Infoview 中，`⊢` 上方是已知，下方是目標。證明的節奏是：讀目標、做一步、再讀目標，直到 No goals。
- 課本上「要證且，分別證兩邊」對應 `constructor`；「這就是已知條件」對應 `exact`。
- `sorry` 讓檔案能編譯，但不代表完成；`#print axioms` 的輸出沒有 `sorryAx`，才代表沒有偷懶。
- AI 從第一章就能幫你**解釋**，但陳述的意義、量詞與假設，必須由你確認。
