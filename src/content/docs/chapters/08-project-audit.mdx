助教改證明作業時，第一件事是看你證明的是不是**題目問的那一句**，再看推論有沒有漏洞。這一章把同樣的檢查用在 Lean 上：先比對 Lean 陳述和課本原題，再看證明依賴了什麼，最後確認你交出的檔案真的完整。把課本習題形式化之後、或拿到 agent 的成果之後，都可以照這一章的清單走一遍。

</UniCourse>

## 本章目標

1. 能對一個 Lean 定理做完整查核，寫成一份另一位同學看得懂的查核紀錄。
2. 辨認常見的「看似正確的錯誤翻譯」：型別、量詞、假設、運算的實際定義。
3. 會用 `#print axioms` 與文字搜尋確認依賴，並正確解讀結果。

## 為什麼需要查核

到這裡，你已經看過很多次這句話：**Lean 只保證證明了檔案中寫的陳述**。這一章把它變成一套具體的流程。和 agent 合作時，查核尤其不能省：agent 的工作是讓檔案通過檢查，而你的工作是確認「通過檢查的東西就是你要的東西」。

查核分三道關卡，順序很重要：

<AuditGates />

## 關卡 1：陳述忠實於原題嗎？

把原題（課本、作業、論文中的敘述）與 Lean 陳述並排，逐項比對。

### 1. 物件與型別

原題的變數是整數、實數、還是自然數？在 Lean 中這是不同的陳述。例如「對所有 x，x 的平方大於等於 x」在 `ℕ` 上為真，在 `ℝ` 上為假（取 x = 1/2）。

### 2. 量詞

每個變數是「對所有」還是「存在」？順序是否正確？[第 3 章](../03-logic-and-quantifiers/) 已經看過 `∀ ∃` 與 `∃ ∀` 的差別。另一個常見問題是**隱含的量詞**：Lean 定理括號中的參數，例如 `(n : ℕ)`，相當於「對所有 n」。

### 3. 假設

原題的每一個前提，Lean 中都有嗎？Lean 中有沒有**原題沒有的**假設？多出來的假設會讓陳述變弱。最極端的情況是假設彼此矛盾，例如同時假設 `0 < x` 與 `x < 0`：此時**任何結論**都能被證明，因為從矛盾可以推出一切。這樣的定理會通過 Lean，但毫無內容。

反過來，**沒被用到的假設**也是一個訊號。真實紀錄中，Codex 在歸納題裡加了假設 `hn`，Lean 警告它沒被用到；AI 把名稱改成 `_hn` 讓警告消失，之後說和課本「數學意義完全一致」（見 [第 4 章](../04-induction-and-sums/)）。改名只是讓警告不再出現，並沒有回答「為什麼這個假設用不到」。查核時看到 `_` 開頭的假設名，請追問：原題需要這個前提嗎？Lean 版本是否其實證明了更一般的敘述？

### 4. 運算的實際定義

Lean 中有幾個運算的定義和日常數學不同，這是為了讓函數處處有定義而做的選擇：

- `ℕ` 上的減法會截斷：`2 - 5 = 0`。
- `ℕ` 與 `ℤ` 上的除法取整數部分：`7 / 2 = 3`。
- `ℝ` 上除以零定義為零：`x / 0 = 0`。

<Term term="截斷減法" short="自然數沒有負數，所以 Lean 規定「小減大」的結果是 0。">

在 `ℕ` 中，`a - b` 在 `a < b` 時定義為 `0`，而不是負數。所以像 `2 * i - 1` 這樣的寫法，在 `i = 0` 時是 `0`，不是 `-1`。課本上「第 i 個奇數是 2i − 1」通常隱含 i ≥ 1；翻成 Lean 時，要確認索引範圍確實避開了 i = 0，或改用不含減法的寫法，並在查核紀錄中說明兩者為什麼一致。

</Term>

所以一個包含除法的陳述，如果原題隱含「分母不為零」，Lean 陳述可能需要明確加上這個假設；反過來，若 Lean 陳述在分母為零時「碰巧成立」，也要確認這不是你想表達的意思。

### 5. 用小例子檢驗

挑幾個具體值，例如 n = 0、1、2 或空列表，手算原題與 Lean 陳述的兩邊。如果結果不一致，翻譯就有問題。這是**檢查翻譯**的工具，不是證明。

### 示範：AI 漏掉一個否定

假設原題是 `¬¬P → P`，AI 卻寫成 `¬P → P`。先不要替它修 proof：這兩句的前提不同，已經不是同一題。回看 [AI101 第 6 集約 1:20](https://www.youtube.com/watch?v=Dqqh1G-CnL8&t=80s)，逐一數清否定符號，再取 `P = False` 檢查第二句：`¬False` 可以證明，但不能因此得到 `False`。

請用三句話回報給 agent：原題的前提是什麼、它改成了什麼、反例如何否定修改後的全稱命題。接著要求它恢復原 statement，再處理 proof。不能新增 `axiom`、增加前提或弱化結論來掩蓋這次改題；即使依賴清單乾淨，也仍要確認證明的是原題。

## 關卡 2：證明依賴了什麼？

### `#print axioms`

對每個主要定理執行：

```lean
#print axioms 定理名稱
```

<Term term="公理（axiom）" short="不經證明、直接被假設成立的命題。">

Lean 的證明最終都要追溯到少數幾條被接受的基本原則。`#print axioms` 會列出某個定理一路追溯下去用到了哪些公理。Lean 與 mathlib 的標準公理只有三條：`propext`、`Classical.choice`、`Quot.sound`，使用它們是正常的。如果有人在專案中自己寫 `axiom 某名稱 : 某敘述`，那條敘述就是被直接「假設成立」，沒有證明。

</Term>

拿到輸出後，依下面三種典型情況判斷：

| 依賴清單中出現 | 代表什麼 | 結論 |
| --- | --- | --- |
| 只有 `propext`、`Classical.choice`、`Quot.sound`，或「does not depend on any axioms」 | 只用了標準公理，或完全不依賴公理 | 正常 |
| `sorryAx` | 證明中（或它引用的某個引理中）仍有 `sorry` | **未完成** |
| 不認識的名字，例如 `my_key_lemma`，而專案中有一行 `axiom my_key_lemma : ...` | 關鍵步驟是被「假設」而不是被證明 | **未完成**，除非原題本來就是「在這個公理下」的命題，而且這件事有清楚寫明 |

第三種最容易被忽略：檔案能編譯、沒有 `sorry` 警告，看起來一切正常，但真正困難的那一步被藏進了一條自訂公理。所以「沒有 sorry 警告」不能取代 `#print axioms`。

### 定義是否被動過

如果原題涉及自訂的 `def`（例如自己定義的數列），請確認定義本身也和原題一致，而且在合作過程中沒有被修改。改定義和改陳述一樣，都是在改題目。

### 文字搜尋

在專案目錄中搜尋 `sorry`、`admit`、`axiom` 這幾個字（VS Code 的全域搜尋即可）。課程的練習檔原本就有 `sorry`，所以要逐一確認每個結果是否都在預期的位置。

## 關卡 3：最終檔案

1. **儲存並實際檢查你交出的檔案**。在專案根目錄對每個練習檔執行 `lake env lean Exercises/檔名.lean`，閱讀完整輸出並記下 exit code。成功結束不代表沒有 `sorry`，要確認輸出中沒有 sorry 警告。`lake build` 只建置課程的參考範例庫 `Course/`，**不會**檢查 `Exercises/`，所以不能用它驗收練習；它適合在你修改了 `Course/` 中的檔案後使用。
2. **差異檢查**。若專案在 Git 中，用 `git diff` 確認合作過程中陳述、定義、import 都沒有被改動；若不在 Git 中，與原始下載的檔案比對。
3. **可讀性**。刪除留在檔案中的 `exact?`、`simp?` 等搜尋指令，換成它們建議的結果；這些指令留在檔案中雖然可能不會報錯，但每次都會重新搜尋。

> **查核提示**：三道關卡的順序不能對調。關卡 1 沒過，後面兩關再完美，證明的也是另一個定理。

## 最後：一段不提 Lean 的數學說明

為每個主要定理寫一段**不提 Lean 的**數學說明：陳述是什麼、證明的主要想法是什麼、哪一步最關鍵。如果你寫不出來，代表你還沒真正理解這個證明，不論它是誰寫的。另外，AI 在文字中說的話（例如「這兩個定理等價」）要和 Lean 實際證明的東西分開看；[第 3 章](../03-logic-and-quantifiers/) 的真實紀錄就是一例。

## 範例：查核前 n 個奇數和

以 [第 4 章](../04-induction-and-sums/) 的 `odd-sum` 為例：

<LeanCode file="Course/Induction.lean" region="odd-sum" />

一份查核紀錄可以這樣寫：

- **原題**：前 n 個正奇數的和等於 n²。
- **型別**：n 為自然數；n = 0 時兩邊皆為 0，原題中「前 0 個奇數的和」按慣例為空和 0，一致。
- **量詞**：對所有 n，由參數 `(n : ℕ)` 表示。
- **索引**：`Finset.range n` 是 0 到 n − 1，第 i 項是 2i + 1，所以涵蓋 1, 3, ..., 2n − 1，共 n 項。手算 n = 3：1 + 3 + 5 = 9。一致。
- **假設**：無額外假設。
- **依賴**：執行 `#print axioms` 後，把**實際輸出**貼在這裡，並註明其中是否有 `sorryAx`。
- **數學說明**：歸納法；步驟中把最後一項 2n + 1 拆出，得到 n² + 2n + 1 = (n + 1)²。

注意「依賴」那一欄：查核紀錄只能寫你實際執行看到的結果。

### 換成你自己的定理

完成 [實戰 1](../../labs/01-proof-repair/)、[實戰 2](../../labs/02-odd-sum/) 或 [實戰 3](../../labs/03-sum-of-squares/) 之後，請挑其中一個定理，照上面的格式寫一份查核紀錄。依賴與建置兩欄一定要貼你自己執行的實際輸出；若還沒執行，就寫「尚未執行」，不要預先寫成通過。好的查核紀錄讓另一位同學不用打開 Lean，也能判斷你的形式化是否忠實於原題。

  task="請 AI 查核一個 Lean 陳述是否忠實於課本原題，再由你逐項確認。"

Finset.range n 包含哪些 i，和原題的 1 到 n 是否一致；\n3. ℕ 上的除法 / 是否會造成問題；\n4. 取 n = 0、1、3，分別手算原題與 Lean 陳述的兩邊。"}
>

- 這個 Lean 陳述其實**翻錯了**。`Finset.range n` 是 0 到 n − 1：多了 0 不影響和，但少了 n。取 n = 3，左邊是 0 + 1 + 2 = 3，右邊是 3 · 4 / 2 = 6。AI 有沒有用小例子抓到這一點？如果它說「忠實」，你就看到了為什麼小例子要自己算。
- 正確的範圍是 `Finset.range (n + 1)`（0 到 n）。也常見把等式改寫成不含除法的「2 倍的和等於 n(n+1)」，這樣就不必討論整數除法。改寫後要在查核紀錄中說明它為什麼和原題等價。
- 關於 `ℕ` 的除法：n(n+1) 一定是偶數，所以這裡的整數除法剛好不會截斷。但這個理由要由你確認，不是只看 AI 說「沒問題」。

</AskAI>

## 練習

### 練習 8.1　找出翻譯問題，再寫出正確版本

以下每一個 Lean 陳述都想翻譯「對所有實數 x，若 x 大於 0，則 x 加上 x 的倒數至少為 2」。先指出各自的問題，再寫出一個忠實的版本並證明它。

```lean
-- (a)
theorem a1 (x : ℕ) (hx : 0 < x) : 2 ≤ x + 1 / x := by sorry
-- (b)
theorem a2 (x : ℝ) : 2 ≤ x + 1 / x := by sorry
-- (c)
theorem a3 (x : ℝ) (hx : 0 < x) (h : x < 0) : 2 ≤ x + 1 / x := by sorry
```

<details>
<summary>提示</summary>

分別檢查：型別、假設是否缺少、假設是否矛盾。對 (a)，算一下 x = 2 時 `1 / x` 在 `ℕ` 中是多少；對 (b)，試試 x = −1。

證明正確版本時，紙上的想法是 $x + \frac{1}{x} - 2 = \frac{(x-1)^2}{x} \ge 0$。在 Lean 中可以先用 `field_simp` 與 `ring` 證出這個等式，再用 `positivity` 說明右邊非負，最後交給 `linarith`。

</details>

<details>
<summary>解答</summary>

(a) 型別錯：在 `ℕ` 中 `1 / x` 對 x 大於 1 時為 0，陳述的意義完全不同（而且 x = 2 時右邊是 2，碰巧成立，但這不是原題）。(b) 缺少 x 大於 0 的假設：x = −1 時右邊是 −2，陳述為假。(c) 假設矛盾：任何結論都能證，這個定理沒有內容。

正確的翻譯是在 `ℝ` 上、只帶 `0 < x` 這一個假設：

```lean
import Mathlib

theorem add_inv_ge_two (x : ℝ) (hx : 0 < x) : 2 ≤ x + 1 / x := by
  have key : x + 1 / x - 2 = (x - 1) ^ 2 / x := by
    field_simp
    ring
  have h : 0 ≤ (x - 1) ^ 2 / x := by positivity
  linarith
```

`field_simp` 需要知道 x 不為零才能消去分母，這裡它由手上的 `hx : 0 < x` 推得；`positivity` 也要靠同一個假設才能確定分母為正。這正好說明 `0 < x` 是必要的前提。(b) 的反例也可以在 Lean 中寫出來：`¬ ∀ x : ℝ, 2 ≤ x + 1 / x`，先 `intro h`，取 `h (-1)`，再用 `norm_num` 得到矛盾。

</details>

## 本章小結

- 查核有三道關卡，順序固定：陳述忠實、依賴乾淨、最終檔案實際檢查過。
- 陳述的常見陷阱是型別、量詞、多出或矛盾的假設，以及 `ℕ` 減法、除法這類運算的實際定義。沒被用到的假設也值得追問。
- `#print axioms` 中出現 `sorryAx` 或自訂公理，就是未完成；查核紀錄只寫實際看到的輸出。
