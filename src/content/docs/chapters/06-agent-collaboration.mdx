這一章沒有新的數學，教的是一個工作習慣：把 AI 當成**幫你跑腿的助手**，而不是代寫作業的人。在大學作業裡最實用的用法有兩種：一是先自己寫好紙上證明，再請 agent 把它形式化，看 Lean 是否同意每一步；二是請 agent 檢查你已經寫好的 Lean 證明，但要求它只指出問題、不要改題。不管哪一種，紙上證明都要先由你寫出來。

</UniCourse>

## 本章目標

1. 分清楚聊天機器人與 coding agent 的差別，並在課程專案根目錄用既有訂閱啟動 Claude Code 或 Codex。
2. 用一份固定的 Prompt 範本委託 agent，明確禁止它修改陳述。
3. 依固定的四步檢查 agent 的成果，自己決定接受或拒絕。

## 從聊天到 agent

前幾章，AI 的角色是「會說話的參考書」：你把 proof state 貼過去，它回答解釋。coding agent 多做兩件事：它會直接改你的檔案，也會自己執行指令並讀輸出。

<Term term="coding agent" short="能直接讀寫專案檔案、執行指令的 AI 工具，例如 Claude Code 與 Codex CLI。">

聊天型 AI 只看得到你貼給它的文字，也只能回你文字。coding agent 在你的電腦上執行，能打開專案中的檔案、修改它們，並執行像 `lake env lean` 這樣的指令、讀取輸出，再決定下一步。所以它可以自己跑「改一行 → 編譯 → 看錯誤 → 再改」的迴圈。能力越大，越需要你事先劃好它可以動的範圍。

</Term>

這讓它在 Lean 上很有用：它可以改一行、編譯、看錯誤、再改。但也帶來新的風險：

- 它可能修改你沒要求它改的地方，例如**定理的陳述**。
- 它可能為了讓編譯通過而加上一個假設、換一個定義，甚至宣告一條 `axiom`。
- 它可能回報「已完成」，但檔案裡還有 `sorry`。

所以本章的重點不是「怎麼讓 agent 寫出證明」，而是**怎麼把 agent 的工作框在你能檢查的範圍內**。下面這張圖是整章的骨架：

### agent 實際會怎麼出錯

本站為了教材，把同樣的課本題目各交給 Claude Code 與 Codex 跑過一次（紀錄說明見 `verification/ai-dialogues/README.md`）。6 份最終答案都通過獨立編譯，但仍然看得到上面說的風險，只是方式比較細微：

- **把警告藏起來**：在歸納題中，Codex 第一次編譯時，Lean 警告假設 `hn` 沒被用到；它把名稱改成 `_hn` 讓警告消失，之後說和課本「數學意義完全一致」。沒被用到的假設本身就值得追問，詳見 [第 4 章](../04-induction-and-sums/)。
- **文字宣稱沒有被 Lean 檢查**：在量詞題中，Claude 證明了兩個定理，並說兩者「等價」，但並沒有在 Lean 中證明這件事，詳見 [第 3 章](../03-logic-and-quantifiers/)。
- **用錯名稱，再自己修正**：在極限題中，Codex 第一次編譯失敗，原因是這個版本的 mathlib 沒有 `abs_add`（名稱是 `abs_add_le`），它接著執行的搜尋沒有結果，之後才改用正確名稱並編譯通過（紀錄看不出名稱從哪來），詳見 [進階：實數序列和的極限](../../advanced/01-limits/)。

這三例都通過編譯。換句話說，「編譯通過」只回答了圖中的③；④還是要你自己做。

## 兩個工具、同一個案例

本章用同一個練習檔示範兩種工具：課程專案中的 `Exercises/ProofRepair.lean`。這個檔案只有一個定理：已知 P 推出 Q、Q 推出 R，證明 P 推出 R。陳述已寫好，證明處用 `sorry` 明確標出待完成的位置：

你可以選擇 Claude Code 或 Codex 其中之一，兩者流程相同；也可以兩個都試，比較它們的行為。

### 共同前提

- 已依照 [環境設定](../../guides/setup/) 完成安裝，並在 VS Code 中確認專案可以正常載入（`Course/First.lean` 沒有紅色錯誤）。
- 已在專案根目錄成功執行過一次 `lake build`。注意：`lake build` 只建置課程的參考範例（`Course/`），**不會**檢查 `Exercises/` 中的練習檔。檢查練習檔要用 `lake env lean Exercises/檔名.lean`，見下文。
- **所有指令都在解壓後的 Lean 專案根目錄執行**，也就是含有 `lean-toolchain` 與 `lakefile` 的那一層。在其他目錄啟動 agent，它會找不到專案。

<details>
<summary>補充：Windows 使用者</summary>

VS Code 可以用原生 Windows 版；Claude Code、Codex CLI 與下一章的 MCP 建議在 WSL 中執行，且專案需位於 WSL 可以存取並能完成 `lake build` 的位置。請不要在同一個專案中混用 Windows 與 WSL 的 Lean 安裝來建置。

</details>

### 登入：使用既有訂閱，不使用 API key

本課程只使用你已經擁有的訂閱方案登入，不需要也**不應該**設定 API key：

- **Claude Code**：在終端機執行 `claude`，第一次啟動時依畫面指示用你的 Claude 帳號登入（之後可在介面中用 `/login` 重新登入）。
- **Codex CLI**：執行 `codex`，依畫面指示選擇以 ChatGPT 帳號登入。

如果你的環境變數中已經設定了 `ANTHROPIC_API_KEY` 或 `OPENAI_API_KEY`（例如以前做別的專案時設的），工具可能改用 API 計費。開始前可以在終端機只檢查「是否已設定」，**不要把金鑰的值印出來**，也不要貼給任何人或任何 AI：

```bash
[ -n "${ANTHROPIC_API_KEY:-}" ] && printf 'ANTHROPIC_API_KEY 已設定\n'
[ -n "${OPENAI_API_KEY:-}" ] && printf 'OPENAI_API_KEY 已設定\n'
```

沒有任何輸出，代表兩者都未設定。若顯示已設定，請先在這個終端機中取消設定（例如 `unset ANTHROPIC_API_KEY`），再啟動工具。本課程不需要任何付費 API 或額外服務。

### 啟動

Claude Code：

```bash
cd 你的解壓路徑/課程專案根目錄
claude
```

Codex CLI：

```bash
cd 你的解壓路徑/課程專案根目錄

```

工具是否逐次詢問，取決於目前的信任、sandbox 與 approval 設定，不能只靠「保持預設」保證。第一次練習時，可以在下方 Prompt 末尾加上：「先只提供一個建議步驟，不要改檔；等我回報 Lean 訊息再繼續。」由你理解後自行貼入工作副本。熟悉流程後，再讓 agent 直接修改指定 proof body；成果仍要依下一節查核。

## 第①步：Prompt 範本

把下面這段文字貼給 agent（兩個工具通用）。之後換成其他練習檔時，只要替換檔名與定理名稱。

```text
你正在協助我學習 Lean 4。專案根目錄就是目前目錄。

任務：完成 Exercises/ProofRepair.lean 中定理 imp_trans 的證明，取代其中的 sorry。
不可直接引用 Course 中的同名參考答案。
檢查方式：在專案根目錄執行 lake env lean Exercises/ProofRepair.lean（不要用 lake build）。

嚴格限制：
1. 不可修改任何 theorem / lemma / example 的陳述（冒號到 := 之間的部分）、名稱或假設。
2. 不可新增假設、修改任何 def，或使用 axiom、sorry、admit。
3. 只能修改該 sorry 所在的證明內容。
4. 最多嘗試 3 輪「修改 → 編譯 → 讀錯誤」。3 輪後若仍失敗，停止並回報目前的錯誤訊息，不要繼續嘗試。
5. 如果你認為陳述本身是錯的或不可證，請停止並說明理由與可能的反例，不要修改陳述。

完成後請回報：
- 你修改了哪幾行；
- 每一步 tactic 對應的數學理由；
- 用來檢查的指令與它的實際輸出（不要轉述成「通過」，請貼出輸出）。
```

這份範本中的每一條都有原因：

- 第 1、2 條防止「為了通過而改題」。這是 agent 最常見、也最危險的失敗模式。
- 第 4 條設定**迴圈上限**。沒有上限時，agent 可能一直嘗試越來越奇怪的 tactic 組合，消耗大量額度，你也越來越難讀懂結果。
- 第 5 條給它一條合法的退路。如果你不給，agent 遇到不可證的陳述時，最容易做的事就是偷偷改它。
- 要求貼出實際輸出，是因為「我已確認編譯通過」這句話本身無法驗證。

### 示範：拿掉限制會怎樣

想體會第 1、2 條的作用，可以做一個對照實驗。先把完成的 `Exercises/ProofRepair.lean` 另存到專案外的筆記資料夾（例如 `ProofRepair.done.lean`），再從原始下載的壓縮檔重新取出這個檔案，讓它回到帶 `sorry` 的狀態；不要直接覆蓋而沒有保留你的成果。接著把 Prompt 中的第 1、2 條刪掉，請 agent 處理同一個定理，觀察它是否修改了陳述或加入假設。

對 `imp_trans` 這種簡單題，agent 多半不需要改陳述就能完成，所以你不一定會看到改題行為；要看得到，得換成 [實戰 1](../../labs/01-proof-repair/) 任務 B 那種刻意「缺前提」的題目。不論結果如何，結束後都要還原檔案。這個實驗要記住的一句話是：**一個沒有被要求保留陳述的 agent，沒有理由保留它**。

## 第④步：檢查 agent 的成果

agent 回報完成後，不要直接相信。請依序自己做：

1. **看差異**。如果你的專案在 Git 中，用 `git diff` 看所有修改；如果不在，用 VS Code 打開檔案逐一比對。確認陳述完全沒有變動，而且只有該處證明被修改。
2. **自己編譯**。在專案根目錄的終端機執行 `lake env lean Exercises/ProofRepair.lean`，記下 exit code，並確認輸出中沒有錯誤，也沒有 sorry 警告。VS Code 中該檔案沒有紅線與黃色警告可以當作輔助確認。不要用 `lake build` 驗收練習：它只建置 `Course/`，就算練習檔有錯也會顯示成功。
3. **查公理**。對該定理執行 `#print axioms`，確認沒有 `sorryAx` 或任何新公理。
4. **讀懂證明**。逐行放游標看 proof state，並對照 agent 給的數學理由。如果某一步你看不懂，請它解釋**那一步**，而不是請它重寫。

如果任一步失敗，先不要套用候選修改；若已寫入檔案，保留差異後回到先前的工作副本修正。是否出現確認視窗，不能取代你對實際修改的查核。

> **查核提示**：agent 說「已完成、編譯通過」只是一句話。你自己跑出的 `lake env lean` 輸出、`git diff` 與 `#print axioms` 才是證據。

## 在大學作業中怎麼用

把上面的流程搬到你自己的證明作業，順序是固定的：

1. **先寫紙上證明**。把課本習題的證明寫在紙上或筆記裡，包括你用了哪些定義與定理。這一步不交給 AI。
2. **自己寫 Lean 陳述，或請 agent 寫但由你檢查**。用 [第 3 章](../03-logic-and-quantifiers/) 的方法檢查量詞順序與假設，用 [第 8 章](../08-project-audit/) 的「原題」清單逐項對照。陳述定案後，才開始證明。
3. **委託證明時套用 Prompt 範本**。把檔名、定理名換掉；可以把你的紙上證明一起貼給 agent，要求它「依照這份紙上證明的步驟」形式化。
4. **用第④步驗收**，並比對 agent 的步驟和你的紙上證明是否一致。若 agent 走了完全不同的路，就請它解釋，或自己對照理解；不要只因為 Lean 通過就把它當成你的證明交出去。

如果課程規定作業不可使用 AI，請遵守課程規定。這時你仍然可以在**繳交後**用這個流程檢查自己的理解。

## 沒有 agent 帳號時

這個流程完全可以手動進行，而且對學習同樣有效：

1. 在 VS Code 中把游標放到 `sorry` 處，複製 Infoview 的 proof state。
2. 嘗試寫一步 tactic，存檔。
3. 如果出錯，把 VS Code「問題」面板中的 Lean 錯誤訊息（diagnostics）完整複製下來，連同 proof state 寫進你的筆記。
4. 讀錯誤訊息，修改，重複。同樣以 3 輪為上限，3 輪後停下來回到課本、重新理解數學。

你也可以把第 3 步的內容貼給任何聊天型 AI，套用同一份 Prompt 範本中的限制，只是由你自己動手改檔案。下一章介紹的 MCP 工具，本質上就是讓 agent 自動完成第 1 與第 3 步。

建議至少手動做一次。例如自己完成下一個練習檔 `Exercises/OddSum.lean`（前 n 個奇數和，需要 [第 4 章](../04-induction-and-sums/) 的歸納法），寫下每一輪的 proof state 與錯誤訊息，最後用 `lake env lean Exercises/OddSum.lean` 檢查。再把這份紀錄和委託 agent 的紀錄放在一起比較：哪一份讓你更理解證明？哪一份花的時間比較少？兩個答案通常不一樣，而知道何時該用哪一種，就是協作的判斷力。

## 練習

### 練習 6.1　第一次委託

用本章的 Prompt 範本，請 agent 完成 `Exercises/ProofRepair.lean` 中的 `sorry`。完成後依「第④步」的四步檢查，並寫下：agent 用了幾輪？你是否接受它的修改？理由是什麼？

<details>
<summary>參考做法</summary>

一份好的紀錄至少包含：任務、輪數、每輪的錯誤訊息摘要（從實際輸出複製，不要自己改寫）、最終 `git diff`、`#print axioms` 的輸出，以及你自己寫的一段數學說明。不要預先填寫結果；每一欄都應該來自你實際看到的畫面。

## 本章小結

- coding agent 會改檔、會執行指令，所以要先用 Prompt 劃好範圍：不改陳述、不加假設、最多 3 輪、不可證就停。
- 協作迴圈中，agent 只負責「修改與編譯」；寫規格與判讀結果是你的工作。
- 「編譯通過」不等於「證明了原題」。真實紀錄中，通過編譯的答案仍有被藏起來的警告與沒被檢查的文字宣稱。
